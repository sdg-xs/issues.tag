# Supported BCF file profile

The initial development profile is BCF XML 3.0. External partner interoperability remains untested until a partner is selected. Official schemas are retained under `tests/bcf_schemas`; their source is [buildingSMART BCF XML release_3_0](https://github.com/buildingSMART/BCF-XML/tree/release_3_0/Schemas).

The issue description remains the primary field. Export derives required Title from its first line and writes the complete Description. TopicType is Issue; supported statuses are Open, In progress, Resolved, and Closed. UUIDs identify topics, comments, and viewpoints. Creation and modification authors and UTC timestamps retain attribution. Optional project.bcfp is omitted because no project metadata is configured. Root bcf.version and extensions.xml declare the profile and status vocabulary.

BCF camera coordinates use metres with Z up; perspective field of view is vertical in degrees. Native camera transforms are converted using the captured stage metres-per-unit and up axis. Component selection uses IFC GUID when the source identifier meets the standard's 22-character requirement; otherwise it uses AuthoringToolId. Scoped Omniverse element metadata can accompany OriginatingSystem, while imported component references remain unresolved until deliberately mapped. No file import creates a spatial pin automatically.

Native hidden-element paths are exported as standard component visibility exceptions using their scoped element identities. External visibility defaults and exception identities are retained for subsequent export. Unknown external identities are not treated as USD paths, so their visibility state needs model mapping before it can be restored locally. Camera positions, directions, and clipping planes convert between captured native units/axes and the standard frame; this does not establish an imported pin attachment.

An optional `omniverse.json` entry per topic preserves the native camera, clipping, selection, visibility, and component scope on this extension's own round trips. Other tools can ignore it. Editable Markup primitives are not exchanged; annotated PNG/JPEG snapshots provide their rendered evidence. Arbitrary partner metadata, documents, coloring, BimSnippet, and editable annotation geometry are outside the supported subset and must be reported when encountered.

Import previews descriptions and statuses against the previous accepted import baseline. A field changed by both sides requires an explicit Keep local or Use imported choice. Comments and viewpoints merge by their stable IDs. Applying a preview fails if its scene or records changed meanwhile. All imported records apply in one undoable issue transaction; imported baselines persist in the parent scene. Imports do not save the scene automatically.

Keep local retains the previous accepted baseline for that conflicting field, allowing a subsequent import to offer the incoming change again. Accepting imported field changes retains their modification author and timestamp. Existing issue creation attribution is preserved. Viewpoint records merge by immutable IDs; an already stored ID keeps its local evidence. Comment edits using an existing comment ID and unsupported metadata are outside the exchange subset.

ZIP content is read in memory, without extraction. Provisional bounds are 100 MiB total uncompressed content and 10,000 members. Duplicate member names, escaping paths, unsupported versions, malformed XML, and XML entity/doctype declarations are rejected. Export replaces its destination only after a complete sibling temporary archive has been written.
